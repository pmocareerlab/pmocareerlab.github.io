Excelが何十ファイルもあって、全部チェックしないといけない。PMOをやっていると定期的に出てくる作業です。

ここでCopilotを使うとき、**任せる範囲を間違えると失敗します。** 「このファイル群をチェックして」と丸投げしても、期待した答えは返ってきません。

実際に使ってみて落ち着いたのは、**チェックそのものは人がやり、その前段階の情報収集だけをCopilotに任せる**という分け方でした。具体的には、必要なデータを集めてくるマクロをCopilotに書いてもらいます。

**この記事でわかること：**

- Copilotに任せる範囲と、人がやるべき範囲の線引き
- マクロを書いてもらうときに伝えるべき情報
- 標準的なビジネス向けCopilotで実際に詰まった点

---

## 任せるのは「判断」ではなく「情報収集」

まず線引きの話です。

大量のExcelをチェックする作業は、2つに分解できます。

1. **必要な箇所のデータを、全ファイルから集めてくる**
2. **集めたデータを見て、おかしいところを判断する**

このうち1はひたすら手間のかかる単純作業で、2は仕様や経緯の理解が要る仕事です。Copilotに向いているのは明確に1のほうです。

{{< note type="experience" title="チェック自体は人間がやる" >}}
私がCopilotに任せているのは、チェックしたいExcelの仕様（どこに何のデータがあるか）と、どんなファイル群があるかを伝えて、**マクロで読み取れる形にするところまで**です。

チェック自体は人間が行います。任せるのは、その前段階の情報収集のマクロ作成だけ。ここを分けておくと、出てきた結果を信用できるかどうかで悩まずに済みます。
{{< /note >}}

判断まで任せると、「この値は仕様上わざとこうなっている」といった例外をAIは拾えません。拾えたかどうかを確認する作業が発生して、結局こちらの手間が増えます。

**集める作業だけを任せれば、間違っていても見ればすぐ分かります。** この違いは大きいです。

---

## 伝えるべき情報は2つ

マクロを書いてもらうときに必要なのは、次の2つです。

### 1. Excelの仕様

どのシートの、どのセル・どの列に、何のデータが入っているか。これを伝えないと、Copilotは一般的なレイアウトを仮定して書いてしまいます。

### 2. ファイル群の構成

どんなファイルが、どこに、どういう名前で置かれているか。ファイル名の規則があるなら、それも含めて伝えます。

{{< comparison-table title="伝え漏れると作り直しになる項目" >}}
| 項目 | 伝えないとどうなるか |
|------|--------------|
| シート名・セル位置 | 一般的なレイアウトを仮定され、読む場所がずれる |
| ファイルの置き場所と命名規則 | 対象ファイルを拾い切れない |
| 1案件あたりのファイル数 | 1案件1ファイル前提で書かれ、2つ目が無視される |
| 集計の単位 | ファイル単位か案件単位かで出力の形が変わる |
| 例外的なファイル | 書式が違うファイルでマクロが止まる |
{{< /comparison-table >}}

この表の3行目は、実際にやってしまった伝え漏れです。

## 一度で完成しない前提で進める

正直に書くと、**一発では完成しませんでした。**

{{< note type="experience" title="伝え損ねた仕様を、後から足して直してもらう" >}}
最初に依頼したときは、1つの案件に対してファイルが2つあるという仕様を伝え損ねていました。当然そこは考慮されていないマクロが出てきます。

そこで改めてその仕様を伝えて、修正してもらいました。やり取りを重ねて仕上げていく形です。
{{< /note >}}

ここで気づいたのは、**人に依頼するときとまったく同じ構造だ**ということです。

依頼が曖昧なら、相手は一般的な解釈で動きます。出てきたものが想定と違うのは、相手の能力ではなく、こちらが前提を渡していないからです。相手がAIでも人でも変わりません。

だから、やり直しを前提に考えたほうが現実的です。**1回目は「こちらの説明の抜けを見つけるための試作」だと思っておく**と、精神的にも楽になります。

→ 依頼の伝え方そのものについては[PMOが人を動かす技術](/posts/pmo-moving-people/)で型を整理しています。

## 標準版のCopilotで詰まった点

万能ではないので、実際に引っかかった点も書いておきます。

**ファイルに書き起こすのが苦手なことが何度かありました。** マクロのコードは生成できても、それを所定のファイルとして出力するところがうまくいかない。

結果として、**マクロに書き込むのは全部手動でやりました。** 生成されたコードをコピーして、自分でVBEに貼り付けて動かす形です。

{{< note type="warning" title="期待値を先に下げておく" >}}
「ファイル生成まで全部やってくれる」と期待して始めると、そこで詰まったときに時間を溶かします。**コードを書いてもらって、設置と実行は自分でやる**と最初から決めておいたほうが早いです。

手で貼る手間は数十秒です。一方、全部読み取って集計する作業を自分で書くと数時間かかります。元が取れないということはありません。
{{< /note >}}

なお、特別なプランでなくても十分使えます。**ビジネス向けの標準的なCopilotでも、ここまでのことはできます。** 高度な機能を契約しないと無理、という話ではありません。

## 業務データを渡すときの前提

ひとつだけ注意点です。

業務のExcelをAIに扱わせる以上、会社のルールの範囲内でやる必要があります。確認しておくべきなのは、契約しているプランで入力内容が学習に使われない設定になっているか、そして社内規程でどこまで許可されているかの2点です。

法人向けのプランは既定で学習に使わない契約になっていることが一般的ですが、**これは契約ごとに違う**ので、自分の環境で確認してください。

→ AIに情報を渡すときのリスクを経路別に整理した記事は[AIに個人情報を入れるリスク](/posts/ai-personal-data-risk/)にあります。

## この使い方がPMOに向いている理由

最後に、なぜこの分け方がPMOと相性がいいのかを書いておきます。

PMOの仕事は、もともと**自分が判断するというより、判断するための材料を整えて渡す**ことの比率が高い職種です。進捗を集め、資料を突き合わせ、課題を一覧にして、判断できる状態にする。

今回のCopilotの使い方は、その構造とそのまま重なります。材料を集める部分を機械に寄せて、判断と説明を自分が持つ。**仕事の形を変えずに、手間の部分だけを削る**使い方です。

そしてこれは評価にも乗ります。PMOの評価では「他のメンバーの工数をどれだけ減らしたか」が見られます。自分の作業時間が減っただけでなく、**チェック待ちの時間が短くなることで周囲の手が空く**のであれば、それは書ける実績です。

→ AI時代に何を身につけるかの全体像は[AI時代のPMOに必要なスキル5つ](/posts/pmo-ai-skills/)、その経験の市場での見られ方は[PMOのスキルは市場で通用するのか](/posts/pmo-market-value/)で扱っています。

## まとめ

- 大量のExcelチェックでCopilotに任せるのは**情報収集まで**。判断は人がやる
- 伝えるべきは「**Excelの仕様（どこに何があるか）**」と「**ファイル群の構成**」の2つ
- 1案件あたりのファイル数のような前提は漏れやすい。**1回目は説明の抜けを見つける試作**と考える
- 標準版のCopilotは**ファイルへの書き起こしが苦手**なことがある。コードは手で貼る前提にしておくと早い
- 特別なプランでなくても、ビジネス向けの標準的なCopilotで十分できる
- 材料集めを機械に寄せて判断を自分が持つ形は、PMOの仕事の構造とそのまま重なる

全部やらせようとすると失敗しますが、**工程を切って渡せば確実に時間が浮きます。**
